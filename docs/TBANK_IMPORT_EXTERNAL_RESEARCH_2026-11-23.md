# Внешний аудит импорта уведомлений Т-Банка — 23.11.2026

## Область и ограничения

Аудит проводится только в лабораторной ветке `feature/tbank-smart-import-lab-1.3.25`. Основная ветка и релизное приложение не изменяются. На этом этапе не добавляется NotificationListenerService и не меняется финансовая модель приложения.

Цель — выбрать проверяемые архитектурные решения для импорта уведомлений Т-Банка, не копируя чужой код и не перенося неподходящие зависимости.

## Исследованные проекты

### 1. Tally Android — jshmartin/tally-android

Источник: https://github.com/jshmartin/tally-android

В README описаны:
- чистый Kotlin parser, отделённый от Android API;
- отдельный recorder, который отвечает за сохранение, дедупликацию, фильтр приложений и отклонённые уведомления;
- Review queue с Keep / Keep all / Discard / Undo и ручным редактированием;
- merchant rules, обучающиеся на пользовательском изменении категории;
- keyword categorizer как fallback, а не обязательная категория;
- защита от повторной публикации того же уведомления и объединение пары уведомлений об одной покупке от разных приложений;
- тестирование parser, categorizer и recorder отдельно; тесты recorder проверяют дедупликацию и отклонения.

Ограничения для ThunBudget:
- правила парсинга в README ориентированы на англоязычные уведомления и валюты США/Европы;
- их merchant aliases и шаблоны не подходят для Т-Банка напрямую;
- README не указывает лицензию на исходный код; до подтверждения лицензии код не копировать и не адаптировать. Использовать можно только общие идеи архитектуры.

### 2. SpendLens / ранее называвшийся UPI Analyser — p4r1ch4y/upi-analyser

Источник: https://github.com/p4r1ch4y/upi-analyser

В README описаны:
- независимое от Android ядро: модели, parser, merchant resolution, fusion, money;
- общий pipeline: parse → dedupe → fuse → resolve → persist;
- шаблоны уведомлений, ориентированные на структуру сообщения, а не только на package name;
- шестиступенчатое разрешение торговой точки: пользовательские правила, имя из уведомления, структура VPA, справочник, fuzzy match, понятный fallback;
- денежные значения целыми единицами минимальной валютной доли, без Double;
- явные veto-правила для неуспешных, будущих и неподтверждённых списаний;
- 102 unit tests и lint без эмулятора;
- тестовый набор на 4 103 сообщениях, из которых 652 были кандидатами, 603 распознаны.

Ограничения:
- проект ориентирован на индийские UPI/SMS шаблоны; банковские фразы, VPA и merchant data не переносятся на Т-Банк;
- проект распространяется под GPL-3.0. Код не копировать в ThunBudget без отдельного решения по лицензионной совместимости. Архитектурные принципы и независимо написанные тест-кейсы можно использовать как исследовательский ориентир.

## Предварительные выводы для ThunBudget

1. Не привязывать весь parser к одному package name. Сначала фильтровать доверенный пакет Т-Банка на уровне Listener, но распознавать структуру сообщения отдельными шаблонами.
2. Разделить pipeline на независимые компоненты: NotificationListener → SourceFilter → Normalizer → Parser → OperationClassifier → Deduplicator/Fusion → MerchantResolver/Categorizer → ReviewQueue → LedgerAdapter.
3. Не сохранять сырой текст уведомлений дольше, чем нужно для локальной проверки. По умолчанию хранить минимум полей; дать возможность удалить исходный текст после подтверждения.
4. Деньги хранить в целых копейках (Long), разбирать через BigDecimal/строгий decimal parser; не использовать Double.
5. Дедупликация должна учитывать source package, notification key/id, временное окно, сумму, направление, нормализованного мерчанта, masked card/account suffix и банковский reference ID, если он присутствует. Одна только сумма+дата недостаточна.
6. Не объединять автоматически две одинаковые покупки одного пользователя. Повторные события от одного источника и вторичные подтверждения от другого источника — разные сценарии.
7. Первые операции и новые форматы уведомлений помещать в Review. Низкая уверенность не должна автоматически менять бюджет.
8. Пользовательские merchant/category rules должны иметь приоритет над словарными эвристиками. Неуверенная категория остаётся пустой.
9. Разделять transfer, own-account transfer, refund, reversal/cancellation, cashback, cash withdrawal/deposit, card purchase, incoming income. Refund не должен становиться обычным доходом.
10. Для поступления от Т-Банка сохранять банковское событие отдельно от IncomeEntry. Пользователь выбирает: связать с уже существующей ручной записью дохода либо создать новый доход. Ручную запись нельзя перезаписывать.
11. Для отмены ошибочного импорта нужна идемпотентная операция удаления/отката и краткосрочный Undo, не удаляющий вручную введённую запись.
12. Listener должен иметь явную диагностику доступа, onListenerConnected/onListenerDisconnected, время последнего события и состояние последней ошибки. Android API требует дождаться onListenerConnected перед операциями с активными уведомлениями.

## Предлагаемая тестовая матрица

### Parser / классификация
- обычная покупка, сумма целая и с копейками;
- варианты форматирования пробелов, запятых и ₽;
- merchant в title, text и bigText;
- перевод исходящий/входящий;
- перевод между собственными счетами;
- зарплата/поступление;
- возврат, отмена, reversal;
- снятие/внесение наличных;
- кешбэк/бонус;
- declined, pending, scheduled, «будет списано», доступный остаток, баланс;
- несколько сумм в одном уведомлении;
- пустое/обрезанное/дублированное содержимое;
- неизвестный шаблон.

### Дедупликация и fusion
- повторный callback одного notification key;
- обновление одного notification key;
- одинаковая сумма у двух разных покупок;
- одна покупка от банка и wallet;
- позднее второе уведомление;
- совпадение суммы, но разный merchant;
- одинаковый merchant и сумма в коротком интервале;
- отсутствие reference ID;
- повторный запуск после перезапуска приложения.

### Категоризация
- пользовательское правило для мерчанта;
- алиасы одного мерчанта;
- кафе/рестораны → «Кафе и развлечения» по согласованному правилу пользователя;
- супермаркеты → «Продукты»;
- неизвестный мерчант;
- конфликт merchant rule и keyword rule;
- исправление категории и повторная операция.

### Доходы и финансовая целостность
- связать банковское поступление с существующим IncomeEntry;
- создать отдельный доход;
- не задвоить итог периода/месяца;
- возврат не увеличить доход;
- own-account transfer не увеличить доход и расход;
- повторная доставка события не изменить баланс повторно;
- отмена импорта не удалить ручную запись.

### Android / Listener — позже на Pixel 8
- доступ включён/выключен/отозван;
- сервис подключился/отключился;
- приложение выгружено системой;
- перезагрузка устройства;
- уведомление пришло при заблокированном экране;
- приложение Т-Банка обновлено;
- формат collapsed/expanded;
- restricted settings для sideloaded APK;
- package name Т-Банка проверен на самом устройстве.

## Дополнительная проверка официальных источников Т-Банка

- Официальная документация по «Операциям по счету» описывает получение выписки и вебхука для счетов компании. Для подключения вебхука требуется письмо с ИНН компании и HTTPS URL; документация говорит об информации о счетах компании. Это не готовый API для личного потребительского бюджета на телефоне. Источник: https://developer.tbank.ru/docs/products/account-info
- Документация по интернет-эквайрингу описывает HTTP(S)-уведомления продавцу о статусах платежей (например, AUTHORIZED/CONFIRMED), а не push-уведомления владельцу личной карты. Источник: https://developer.tbank.ru/funding/intro/developer/notification
- В публичном обсуждении импорта SMS 2017 года приведены исторические примеры Тинькофф («Покупка. Карта *XXXX…», «Перевод…»). Это SMS-форматы старого поколения, не подтверждённые как актуальные Android push-форматы. Их можно использовать только как дополнительные негативные/регрессионные примеры, но не как основной parser contract. Источник: https://community.personalfinances.ru/d/349-import-tranzakciy-iz-sms-soobscheniy/73
- Android API предоставляет `NotificationManager.isNotificationListenerAccessGranted(ComponentName)` для точной проверки выданного пользователем доступа. Сам Listener должен ожидать `onListenerConnected()`; после отключения есть отдельный callback `onListenerDisconnected()`. Источники: https://developer.android.com/reference/android/app/NotificationManager и https://developer.android.com/reference/android/service/notification/NotificationListenerService

Практический вывод: пока не найден публичный официальный API, который подходит для чтения личных карточных операций в персональном приложении ThunBudget без бизнес-счёта. Основной проверяемый путь для этой задачи остаётся Android NotificationListenerService с явным разрешением пользователя, плюс ручной/файловый импорт выписки как отдельный возможный резервный канал.


## Пользовательские правила категоризации по реальным скриншотам Т-Банка (23.11.2026)

Эти правила заданы владельцем ThunBudget и имеют приоритет над банковской категорией и общими ключевыми словами.

| Категория/тип операции в Т-Банке | Категория ThunBudget |
|---|---|
| Фастфуд, кафе, рестораны, развлечения | Кафе и развлечения |
| Бензин, заправки, автоуслуги, транспорт | Транспорт |
| Связь, ЖКХ | Жильё и ЖКХ |
| Цифровые товары, наличные (категория покупки), красота, исходящие переводы | Личные расходы |
| Снятие наличных (тип банковской операции) | Другое |
| Аптеки | Здоровье |
| Различные товары | Другое |
| Неидентифицированные расходы | Другое |
| Супермаркеты | Продукты |

### Важные условия

- «Наличные» как категория расхода и «снятие наличных» как банковское событие — разные случаи. Первое → «Личные расходы», второе → «Другое».
- Категория «Переводы» на скриншотах содержит исходящие списания. Для входящего перевода нельзя применять правило личных расходов: его направление должно быть определено отдельно как поступление и отправлено на согласованный сценарий доходов.
- Перевод между собственными счетами не должен становиться расходом или доходом; если это нельзя надёжно определить, требуется подтверждение пользователя.
- Если категория Т-Банка неизвестна или не сопоставлена, не угадывать категорию по умолчанию: «Другое» только для расходов, а сомнительный тип операции отправлять на ручную проверку.
- Слова «перевод», «наличные» и «связь» сами по себе недостаточны для классификации без проверки направления и типа события.

### Данные, извлечённые со скриншотов (reference fixtures)

Скриншоты показывают историю операций/категорий в приложении Т-Банка, а не текст push-уведомлений. Поэтому они являются эталонами для категоризатора и нормализации мерчантов, но не подтверждают формат NotificationListener payload.

Наблюдаемые категории и примеры:
- Переводы: исходящие переводы физическим лицам и организациям; категория назначения по правилу владельца — «Личные расходы».
- Рестораны: Kula Bar, «Перцы», Genatcvale, «Торговый павильон»; назначение — «Кафе и развлечения».
- Супермаркеты: Магнит, «Русский Разгуляйка», Imperiya; назначение — «Продукты».
- ЖКХ: УК Перспектива, Сибирская Теплосбытовая Компания, УК ЖСК, ГИС ЖКХ; назначение — «Жильё и ЖКХ».
- Заправки: Газпромнефть; назначение — «Транспорт».
- В панели «Остальное» перечислены Фастфуд, Наличные, Аптеки, Цифровые товары, Красота, Развлечения, Различные товары, Связь, Автоуслуги, Другое, Местный транспорт. Применять заданное владельцем сведение: фастфуд/развлечения → «Кафе и развлечения»; связь → «Жильё и ЖКХ»; автоуслуги/местный транспорт → «Транспорт»; цифровые товары/наличные/красота → «Личные расходы»; аптеки → «Здоровье»; различные товары и «Другое» → «Другое».
- На одном скриншоте другого приложения показан пример мерчанта КрасАвтоТранс с отдельными повторяющимися списаниями по 48 ₽. Это полезный пример для проверки повторных небольших транспортных платежей: одинаковые суммы и один мерчант не должны автоматически дедуплицироваться как одна операция.
